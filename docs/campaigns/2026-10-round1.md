# 首轮公开评测（2026-10-04 至 10-05）

用平台正式流程评测：每个评测都用 `crucible submit agent ... --public` 经 Worker 提交，在 GitHub Actions 上构建、运行、打分，结果回传 Worker 并进入排行榜。时间均为太平洋时间（PDT）。

## 结论

1. **写代码类，Octos 改进版（octos-arc PR #269）最好**：hello-world、todo-mini、bookclub 三个题目包全部满分，3 遍结果完全一致。
2. **Codex 第二**：hello-world 满分，todo-mini 88%，bookclub 88%。丢分是零散的个别检查项，不是整体做坏。Codex 每个阶段都很快自己结束（大多 1–7 分钟，时限 15–20 分钟）。
3. **Octos main 最差**：hello-world 17%，todo-mini 58%，bookclub 27%，而且每遍之间差别很大。日志显示几乎每个阶段都卡在同一个问题上：内部流水线模板里有未转义的花括号，调用被拒，只能把兜底产出交上去。PR #269 修的正是这个问题，改进版的日志里这类报错一次都没有。
4. **写代码的三个小题目包，成本都很低，三者接近**：按公开价格折算，每遍（整套题目包）约 0.3–7 美分。用的是 GLM 包月套餐，这个数字只用来横向比较。todo-mini 上 Codex 稍便宜（$0.034 对 $0.040），bookclub 上 Octos 改进版便宜（$0.050 对 $0.071）。Octos main 花的钱和改进版差不多，但分数低很多，单阶段用时长 2–7 倍（常常把预算耗尽才停）。
5. **数学证明**：math-prover 两道 IMO 题 3 遍都是满分（14/14）。这两道是经典老题，这个演示题目包区分不出强弱。
6. **ARC-Bench GitHub 题阶段 1（只评 Octos main，2 遍）**：两遍都是 11/30（37%），每遍约 71 分钟、等价花销约 0.49 美元，是本轮最贵的一项。这道题上没出现上面的模板报错：流水线正常跑起来，但到预算用完也没做完，交出部分产出。
7. **巡天参照**：入门包示例观测 agent 走 app 模式，L1–L4 得分为 4458.56 / 4767.70 / 4276.82 / 3499.91，四卡合计 17002.99。结果是确定的，L1 与文档里的值一致。
8. **429（限流）一次都没有**：全程最多同时跑 2 个评测（每个 3 遍并行），GLM 没有限流。
9. **平台问题**：Worker 的 KV 每日写入额度用完，导致约 3 小时提交不了（未修，见下文）；另修了 2 个问题：CLI 在评测其实已失败时报“提交成功”（#58），Codex 包构建失败（#59）。

## agent 的典型失败（只看分数和 agent 自己的日志）

- **Octos main**：几乎每个阶段，日志里都是 `run_pipeline` 被拒：“arc_build 流水线的节点提示词引用了未绑定的模板变量”。agent 重试 2–3 次，同样被拒，然后耗尽预算（约 8–14 分钟），交出兜底产出。hello-world 6 个阶段里有 4 个连前端构建都失败（`npm run build` 找不到 `src` 目录）。bookclub 有一遍三个阶段全是 0 分。agent 自报的 token 常常只有几百到几万，比计量代理记录的少得多；本报告一律以计量代理为准。
- **Octos 改进版**：没有失败。每阶段 2–7 分钟内自己结束，日志里没有被拒的调用。
- **Codex**：所有阶段都是自己正常结束（`codex exit: 0` 或时限前退出），远没用完时限。todo-mini 有一遍第 3 阶段 0/4，bookclub 第 1 阶段两遍各少 1 项、第 3 阶段一遍只过 2/6。日志里看不出崩溃，属于功能细节没做对。另外 Codex 启动时会请求 `/v1/models`，计量代理返回 404，不影响运行。
- **math-prover**：没有失败。

## 发现的平台问题

### 已修

1. **CLI 在评测已失败时报“提交成功”**（[#58](https://github.com/octos-org/octos-crucible/pull/58)，已合并）。Worker 写 KV 失败时先把评测记为 failed、再返回 503；CLI 把 5xx 当网络错误重试，第二次得到 409，查到评测存在，就当成“第一次其实成功了”，打印 eval_id 并正常退出——评测其实从未启动。现在查到状态是 failed 会报错退出，并在每次 5xx 重试前打印 Worker 给的原因。
2. **Codex 包构建失败**（[#59](https://github.com/octos-org/octos-crucible/pull/59)，已合并）。第一次真跑，3 遍都在构建时报 `cannot update the lock file ... because --locked was passed`：Codex 的 rust-v0.93.0 tag 改了工作区版本号，但没更新 `Cargo.lock`。构建前加 `cargo update --workspace`（只改工作区成员自己的版本号，外部依赖不变），之后 3 个题目包都能正常构建运行。

### 未修（建议）

1. **Worker 的 KV 每日写入额度用完，约 3 小时无法提交 agent 评测**（10-04 13:47 到 17:00 PDT）。凭据存在 Workers KV，免费额度每天 1000 次写入，00:00 UTC（17:00 PDT）重置。代码里只有“写入凭据 / 删除凭据”两处写 KV，每个评测 2 次，按理很难用完；额度是谁用掉的，需要在 Cloudflare 后台看。用完后网页和 CLI 都无法提交带模型的评测（只打分、不用模型的 app 模式不受影响）。建议：把凭据改存 D1（每天 10 万行写入，评测结束删除），或者升级付费计划；同时在网页上明确提示“今日额度用完，几点恢复”。
2. **排行榜把“部分评测”和完整评测放在一起排**。每个（用户, agent）只取总分最高的一次，但不区分这次评测跑了哪些阶段：巡天的 4 张卡是 4 个单卡 app 评测，榜上只剩最高的 L2（4767.70），标题却是“四卡总分”；arcbench 只跑阶段 1 的评测也会和跑满 3 个阶段的评测比总分。建议：只让跑满全部阶段的评测上榜，或按“跑了哪些阶段”分开排。
3. **上传的 agent 包没有镜像构建缓存**：Codex 每遍都从源码编译（约 17–18 分钟），3 遍就是 3 次。建议对相同的包哈希缓存镜像。
4. **全部 replica 构建失败时，用户只看到 failed，看不到原因**：publish 步骤打包下载文件时因为“没有任何产出”报错退出，manifest（里面有“stage-1 did not run”等原因）没有回传 Worker。建议这种情况下跳过下载包，照常回传 manifest，并保持 failed 状态。
