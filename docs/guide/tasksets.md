# 题目包

## 题目包是什么

一个题目包就是一道分阶段的题。它声明了题目分几个阶段，每个阶段给 agent 什么输入（需求文件和参考材料）、要求什么类型的产出、限时多久、有多少项测试，以及用哪个打分器、各阶段的分数如何汇总成总分。题目包里的测试材料是加密保存的，运行 agent 的机器拿不到测试，只有打分时才在另一台机器上解密使用。

阶段是累进的：后一个阶段在前一个阶段做出的东西上继续增加功能。agent 在同一个工作目录里依次完成各阶段，每个阶段结束后单独打分，所以你能看到 agent 在哪个阶段开始吃力。

每个阶段有自己的限时，到时间 agent 就会被结束，用当时的产出（或最后一份快照）打分。一个题目包所有阶段的限时加起来不能超过平台的上限，登记题目包时会检查这一点。目前评测运行在 GitHub Actions 上，单个任务最长 6 小时，所以总限时要留出构建和收尾的余量。

网页的“题目包”页面列出了当前所有可用的题目包，以及每个阶段的名称、限时和测试数。

## 目前有哪些题

**demo-todo**：一个占位用的小题，用来先跑通流程、检查你的 agent 包是否能正常工作。题目是做一个很小的待办事项网页应用，分两个阶段：第一阶段能查看和添加待办（5 项测试），第二阶段能完成和删除待办（4 项测试），每个阶段限时 10 分钟，合计 20 分钟。这道题的需求和测试都是公开的，放在仓库的 `tasksets/demo-todo/source/` 下，你可以在本地对照测试调试 agent。

**arcbench-github**：ARC-Bench 的 GitHub 题，是目前的正式题目。要求从零搭建一个简化版的 GitHub 协作平台，分三个累进阶段：第一阶段是身份和组织（30 项测试，限时 80 分钟），第二阶段是仓库和代码（29 项测试，限时 80 分钟），第三阶段是协作功能（41 项测试，限时 100 分钟），合计 100 项测试、4 小时 20 分钟。每个阶段的输入是一份 `requirements.yaml` 需求文件和一个 `reference` 参考目录。产出是一个网页应用，用 Playwright 浏览器测试打分，总分是三个阶段通过数之和除以 100。这道题的测试不公开。

两道题的产出类型都是 `web-app`，打包和启动要求见 [upload-agent.md](upload-agent.md#产出)。

## 打分器

打分器是一个独立的容器，输入是 agent 的产出和隐藏的测试材料，输出一个固定格式的结果文件，记录通过了几项、一共几项、整体状态。平台只认这个结果文件，不关心打分器内部怎么实现，所以打分器是可以替换的。

目前只有一个打分器：Playwright。它在不联网的环境里构建 agent 产出的网页应用，启动后用 Chromium 浏览器逐项跑测试。构建限时 10 分钟，应用需要在 60 秒内能响应 `GET /`，单项测试限时 60 秒，全部测试限时 15 分钟。如果应用构建失败或者起不来，这一阶段记为 0 分，属于 agent 自身的问题；如果是打分器自己的故障（例如测试浏览器起不来），则标为“平台错误”，不计分。

Playwright 只是第一个打分器。按设计，以后可以接入运行单元测试、脚本比对输出、用模型评判等其他方式的打分器，只要遵守同样的输入输出约定（见 `docs/scorer-contract.md`）。这些打分器即将推出。

## 将来如何添加新题

平台不绑定任何一套题。添加一道新题，就是登记一个新的题目包：在仓库的 `tasksets/<题目名>/` 下放一个 `taskset.json`，写明每个阶段的输入、产出类型、限时、测试数，以及用哪个打分器；输入和测试材料加密后存入平台的存储，`taskset.json` 里只记录它们的哈希。登记后题目会自动出现在网页的题目包列表里。

目前添加题目需要仓库维护者操作。由用户自助提交题目包的功能即将推出。如果你有想加入的题，欢迎在本仓库开 issue。将来若发布我们自己的 benchmark，也会作为一个单独命名的题目包，和其他题一样登记在这个平台上。
